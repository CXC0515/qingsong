# ADR-001：青松接入Harness的运行与数据边界

版本：1.0 · 2026-10-26
状态：推荐决策，待整体方案评审；本轮仅文档。
关联：[整体架构2.0](../ARCHITECTURE.md)

## 问题与约束

多位教师需要各自连续的规则、记忆和任务状态，同时复用青松已有登录、业务服务和资料。必须防止运行身份漂移、全局指令串用户、写入重复和“日志完成但业务未保存”。当前个人工作区是一人一工作区，组织共享尚未实现；当前服务器的Harness容量未实测。

## 推荐决策

1. 保留青松UI和服务端鉴权，官方SDK连接独立Harness进程；优先评估sdk profile并显式收窄工具，复用框架原生循环、会话/持久化、指令与技能机制。
2. 使用共享运行管理器，按userId+workspaceId分配home、agents目录和运行租约；进程按需启动/回收，持久状态不随进程销毁。目录分区不等于OS隔离，沙箱、凭据与越界测试是上线门槛。
3. 规则、长期记忆、审批和业务回执由青松管理；AGENTS.md是有效规则的可重建投影。原生会话保留执行过程，业务库保留已提交事实；不用聊天摘要代替任一权威数据。
4. 教学业务契约先独立于传输，第一版推荐薄插件+受控内部RPC；有跨客户端需要时增加MCP适配。SDK与MCP职责不同，无需二选一。
5. 写入绑定具体预览/版本/参数和operationId；结果不明先查询业务回执，再补会话反馈。不得仅靠模型最终输出确认业务成功。

## 备选与代价

| 方案 | 优点 | 未采用为默认的原因 |
| --- | --- | --- |
| 直接嵌入官方Web | 快速看到框架能力 | 青松身份、教师场景、业务审批和资料引用仍需接入，形成第二套界面与账号边界 |
| 一个共享Harness进程动态切换教师环境 | 进程数量少 | 进程级home/指令与凭据易串用，生命周期及撤权难以核验 |
| 每教师完整部署青松与Harness | 部署边界直观 | 重复业务服务、升级和资源成本；隔离运行不需要复制整套产品 |
| sdk-minimal+按需补齐 | 组合显式、可裁剪 | 默认仍有通用执行工具，且缺少指令/Skills等服务；补齐与验证成本需和sdk裁剪比较 |
| 第一阶段固定HTTP MCP | 便于其他客户端复用 | 新增凭证、网络与运维面；并不能省略SDK连接和业务契约 |
| 直接修改Harness内部循环 | 灵活 | 增加升级负担，重复已有能力，业务策略可在官方扩展点实现 |

## 后果与验证

收益：个体上下文、任务恢复与业务控制有清晰所有者，框架升级边界较小。成本：需要运行管理器、受控插件/工具层、记忆治理和跨存储结果核对；独立进程占用须测量，不能据此承诺多人并发容量。

实施前用固定版本验证：注册工具允许列表；两教师home/会话/记忆/资料越界；宿主凭据不进入模型；断线/重启/审批过期；业务已提交但会话回执缺失；原生会话flush和关闭；撤权后的历史上下文不可直接复用。当前没有执行这些集成测试。

## 变更依据

从v1.1的“建议教学业务MCP服务”升级为“SDK连接引擎、统一业务契约、MCP按需适配”；从笼统的共享实例升级为共享业务服务和隔离的运行命名空间。用户认可的是五层产品结构，未将本ADR的全部技术选择视为已批准实施。
