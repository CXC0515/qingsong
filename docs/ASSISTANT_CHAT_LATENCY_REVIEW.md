# 会话发送反馈与历史加载调查

版本：0.1 · 2026-10-28 · 状态：只读代码调查与修复建议，正式代码未修改。

## 用户现象与判断边界

用户报告：有时发出消息后没有及时反馈，过一会儿内容突然出现；每次进入和切换会话，历史加载仍慢。原型授权已确认，但这两项正式问题目前只做调查与方案；没有浏览器、生产计时或真实模型复现，不能宣布根因已确定或已修复。

两个问题应先于长期 Memory 扩展处理：教师首先需要知道请求是否收到、当前是否在等待、结果是否可靠；否则更多记忆和可写能力会放大重复发送、误判与状态混乱。

## 已确认的代码事实

| 层级 | 证据 | 含义与限制 |
| --- | --- | --- |
| 本地发送反馈 | 当前 DSH rc.3 的 conversation.sendSession 调用 beginSubmission，随后等待 nextPaint 再序列化和 prompt；Session 有 pendingSubmissions | 已有本地回显机制。不能直接认定“没有做乐观消息”；需检查实际迟滞是否发生在回显绘制、回显退休/替换或首个服务端事件 |
| 全局排队 | official-teaching 的 agent/pre-step 等待 bridge acquire，服务端等待 officialBudget.acquire 才结束该请求 | 首次模型调用前可能排队；当前这条桥接链没有将等待阶段作为明确的队列状态传给用户界面。不能将这段时间统一写成“模型思考中” |
| 历史窗口 | Session.doOpen 打开 SessionEventStream；通过 session.follow 建立历史与实时流一致基线；默认最少50条消息/2轮、上限500条 | 历史不是纯文本文件请求，还包括基线和投影。是否过大、是否重复打开要实测，不能直接缩成很小的页破坏轮次或连续性 |
| 会话驻留 | Session 源码明确驻留，Workspace.replaceMain retain新对象再release旧引用 | 已有会话保留基础。需要核对重复开流、重同步和驻留实际效果，不先另建一套历史库 |
| 请求入口 | ensureInstance 在复用实例前仍依次执行授权、models()及配置指纹；models读取/引导模型配置，fingerprint读取配置文件 | 每次代理请求均有前置工作，可计量与优化；尚未证明这些本地读取是主要耗时，授权检查不可因优化而删除 |
| 冷启动 | 实例闲置超过10分钟后可能被回收；启动包括运行时、认证交换和默认工作区准备 | 首次打开与热切换应分开统计。不能把所有切换延迟都解释成冷启动 |
| 已有观测 | HTTP有Server-Timing instance/upstream，启动有分段日志；外壳ready等待工作区和会话列表就绪 | 这些信息未覆盖点击到回显、首事件、首内容和历史首次可见。ready也不证明当前会话历史已可读 |

上述依赖源码均来自本机锁定版本，不涉及升级或改写 node_modules。

## 原型 v2 中先验证的反馈设计

- 点击发送即显示本地消息及“正在发送”，不提前称为服务端已收到。
- 收到确认后区分等待处理与实际执行；演示排队时持续显示已接收状态。
- 历史切换立即更新会话标识；缓存内容只能属于目标会话。没有缓存时明确显示目标会话正在读取，有缓存则保留并提示更新。
- 回调按会话归属更新。切换期间保留各自草稿，旧会话的迟到响应不能覆盖当前会话。
- 操作断线显示结果未知，按原编号核对，不能给出误导性的重复提交按钮。此处模拟业务回执，不代表正式助手已获得写入能力。

## 正式修复的最短路径（待代码范围批准）

### 第一步：补齐观测与确定性慢链路验证

统一请求/会话关联标识，仅记录耗时、状态和计数，不记录教师消息或学生内容。测量：点击→本地回显；请求→接收确认；排队时长；开始处理→首事件/首内容；点击会话→缓存可见/历史基线可见；事件缺口重连次数。实时流的首帧与持续时长单独记录，不能用普通HTTP头的upstream耗时代替。

使用隔离临时数据与模拟模型分别制造：接收确认慢、队列占用、首内容慢、历史慢、断流、快速连续切换。现有依赖具备回显和驻留，应先定位为何体验未满足，再决定是否需要更换呈现插槽或调整生命周期。

### 第二步：修复反馈与查明的重复工作

通过受支持的DSH服务/插槽展示当前阶段，不对压缩DOM做脆弱补丁，不直接修改node_modules。核对并修正本地回显与服务端持久消息合并的空档；失败保留草稿、未确认状态与人工恢复入口。优先显示目标会话已有快照，后台校验新基线；防止重复开流和过时结果覆盖。

如果计时证明入口模型/配置检查显著，再以配置版本或受控失效缓存去除重复工作，维持实时身份/权限校验、模型配置更新和撤权语义。若首帧流传输慢则沿WebSocket代理与缓冲链检查；若页面渲染慢则检查消息装配、长内容和滚动定位。仅改加载文案不足以关闭性能问题。

### 文件范围建议

- `agent/official-ui/client.js`、`agent/official-ui/shell.css`：原生扩展状态显示与反馈；优先复用现有服务和投影。
- `server/services/assistant/officialAssistant.ts`、`officialBudget.ts`：请求分段计时和可信排队状态；仅在证据支持时优化实例前置检查。
- `agent/official-teaching.mjs`、必要的 relay 文件：传播执行阶段及流计时，具体接口经依赖契约核对后确定。
- `src/features/assistant/AssistantPanel.tsx`：仅在外壳阻挡或连接反馈确有问题时修改，不重复维护原生会话状态。
- 现有原生/HTTP集成检查及专项文档：补慢链路、隔离、重连、连续切换的验证。

上述是建议上限，并非已批准修改所有文件。实现前根据第一步证据收敛准确范围；若依赖缺少所需扩展点，先提交适配或版本方案，不自行升级DSH。

## 取舍、风险与验收

不选“加一个无限转圈”作为完整修复：只能缓解困惑，无法解释丢回显或重复加载。不选直接增大全局并发：没有资源与隔离测量，可能降低稳定性。不选永久缓存历史：可能掩盖新消息、权限变更和过时记录。

建议本地回显在点击后的下一次可绘制帧出现，不受网络/模型等待影响；这是一项待验证目标，不是实测结果。热切换同一已驻留会话不应为了再读历史而先清空已知内容；首次加载、长历史和断线恢复分别记录p50/p95，再确定性能目标。失败提示说明消息/业务是否确认保存及下一步，避免状态未知时说“未保存”。

自动检查证明协议和状态边界；浏览器、手机与真实网络/模型延迟由用户验收。本轮没有生产计时，未承诺加速倍数或毫秒数。
